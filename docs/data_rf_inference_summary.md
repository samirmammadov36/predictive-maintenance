# Data, Random Forest, and Saved-Model Verification

## Scope

This document covers the inherited Task 29 responsibility: test and document the FD001 data loader, RUL target calculation, Random Forest pipeline, and saved-model usage. It also records the prediction contract that the shared inference layer must preserve.

The reusable multi-model inference module itself belongs to Task 25 and is handled separately. Task 29 verifies the data/RF side that Task 25 must consume.

## FD001 Raw Data Loader

The raw NASA C-MAPSS FD001 train and test files are loaded by `read_cmapss_file(...)` in `src/predictive_maintenance/data.py`.

Each raw row has 26 columns:

- `engine_id`
- `cycle`
- three operating settings: `setting_1` to `setting_3`
- 21 sensor measurements: `sensor_1` to `sensor_21`

The loader assigns this fixed schema, converts engine ID and cycle to integers, sorts rows by `engine_id` and `cycle`, and returns a zero-based pandas index. The raw files remain the reproducible source; generated processed data and model artifacts are intentionally ignored by Git.

## Training RUL Targets

Training RUL is generated by `add_training_rul(...)`.

For every training row:

`rul_true = final cycle of that engine - current cycle`

`rul_true` is kept uncapped for evaluation/reference. The fitting target is stored separately as `rul_target` and capped at 125 cycles:

`rul_target = min(rul_true, 125)`

Therefore the final run-to-failure row of each training engine has `rul_true = 0`, while early-life fitting targets above 125 are clipped to 125.

## Official Test RUL Mapping

The official `RUL_FD001.txt` file contains one remaining-life value per test engine. `read_test_rul(...)` assigns these rows to engine IDs using one-based row order: the first RUL value belongs to engine 1, the second to engine 2, and so on.

`official_test_targets(...)` then creates exactly one evaluation row per official test engine at that engine's final observed test cycle. The RUL value is the provided official uncapped label; it is not calculated from the visible test trajectory itself.

This distinction is important because the test trajectories stop before failure. Evaluation therefore compares one prediction at each engine's final observed cycle against the corresponding official RUL label.

## Development Split and Validation Target

The development split is engine-level rather than row-level. With seed 42, 80 engines are used for training and 20 for validation.

For each validation engine, the visible validation prefix ends at `floor(0.70 × full trajectory length)`. The model sees only that prefix. The validation truth is calculated from the hidden future of the full training trajectory as:

`true RUL at prefix = final cycle - visible prefix end cycle`

This avoids selecting models at the final failure row, where the true RUL would always be zero.

## Random Forest Input Pipeline

Random Forest and XGBoost share the same tabular preprocessing path.

After training-only sensor screening and clean median recovery, `build_tabular_features(...)` creates:

- current operating cycle
- current values of the 15 frozen selected sensors
- causal 10-cycle rolling mean for every selected sensor, with `min_periods=1`
- causal 10-cycle difference for every selected sensor

With 15 selected sensors, this produces 46 model features in total: one cycle feature plus 45 sensor-derived features.

Operating settings and engine ID are not model features. The `StandardScaler` is fitted only on engineered rows from the 80 training engines, and its frozen column order is stored in the prepared bundle/schema.

## Random Forest Training and Selection

`train_random_forest(...)` evaluates a small deterministic search using `random_state=42`:

- `n_estimators`: 250 or 450
- `max_depth`: `None` or 16
- `min_samples_leaf`: 1 or 2

Configurations are selected by clean validation-prefix RMSE, with MAE as the tie-breaker. Official test labels are not used for tuning.

The selected configuration recorded in `results/metrics/validation_selection_summary.json` is:

- `n_estimators = 250`
- `max_depth = None`
- `min_samples_leaf = 1`
- validation MAE: approximately `17.03` cycles
- validation RMSE: approximately `22.54` cycles

The fitted model is saved as `artifacts/models/random_forest.joblib`.

## Saved-Model Prediction Contract

For a clean Random Forest prediction at an observed engine prefix, the saved-model path is:

1. use only the rows available in the engine prefix
2. use the frozen selected sensor columns
3. recompute the causal tabular features on that prefix
4. take the latest engineered row in the frozen feature-column order
5. apply the saved training-only tabular scaler
6. call the saved Random Forest model's `predict(...)`
7. clamp a negative prediction to zero
8. interpret the result as Remaining Useful Life in operating cycles

The current Streamlit application follows this contract for its inline RF prediction path. Task 25's reusable inference module should preserve the same ordering and preprocessing objects rather than introducing a second RF preprocessing implementation.

## Official Clean Random Forest Result

The committed clean official FD001 comparison reports:

- MAE: approximately `15.25` cycles
- RMSE: approximately `21.30` cycles

These metrics are calculated on all 100 official test engines, with one prediction per engine at its final observed cycle and the official uncapped RUL label as truth.

## Automated Tests

`tests/test_data_rf_pipeline.py` adds focused Task 29 checks for:

- the official 26-column C-MAPSS loader schema and row ordering
- uncapped training RUL truth plus capped fitting target behavior
- one-based mapping of `RUL_FD001.txt` rows to test engine IDs and final observed cycles
- Random Forest prediction consistency after a Joblib save/load round trip using the same causal tabular feature pipeline

These complement the existing core tests for split isolation, causal features, imputation, masks, and sequence boundaries.

## Real-Artifact Verification

Run the following after the normal data preparation and training steps:

```text
python scripts/verify_data_rf_pipeline.py
```

The script loads the actual generated `prepared_bundle.joblib` and `random_forest.joblib` and verifies:

- official test engine IDs and target IDs match one-to-one
- every target row is attached to that engine's final observed cycle
- saved scaler/model feature counts match the frozen schema
- saved Random Forest hyperparameters match the selected validation configuration
- fresh predictions from the saved Random Forest reproduce the committed clean MAE/RMSE within numerical tolerance

A successful run writes `results/metrics/data_rf_verification.json`. This file is small and can be committed as verification evidence after the script passes.

The final integration owner can then call that shared inference code from Streamlit instead of maintaining duplicate model-loading/preprocessing logic in `app.py`.
